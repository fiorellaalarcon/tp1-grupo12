Registro breve del proceso

Qué hicimos, qué decidimos y qué resolvimos

Este resumen funciona como una lectura rápida de la bitácora. Las secciones siguientes desarrollan cada etapa con mayor detalle y la relacionan con su evidencia técnica.

  1. 1 · Definimos el problema y el concepto

    Hicimos: retomamos la problemática de logística B2B y analizamos alternativas para el TP1. Decidimos: construir Eximia Code como empresa ficticia de software para mantener un mismo dominio entre materias.

  2. 2 · Organizamos el trabajo del equipo

    Hicimos: distribuimos roles según las fortalezas y áreas técnicas de cada integrante. Decidimos: que cada perfil tuviera una responsabilidad y una interacción relacionada con ese rol.

  3. 3 · Diseñamos una base común

    Hicimos: definimos identidad visual, arquitectura modular, navegación, responsive y accesibilidad. Resolvimos: el riesgo de que cinco perfiles parecieran sitios distintos mediante tokens, componentes y criterios compartidos.

  4. 4 · Pasamos de la planificación a ramas independientes

    Hicimos: distribuimos la implementación en ramas por integrante. Decidimos: integrar mediante Pull Requests para conservar responsables, cambios y contexto de cada incorporación.

  5. 5 · Encontramos problemas durante la implementación

    Resolvimos: overflow en pantallas pequeñas, carga innecesaria de multimedia, peso de imágenes, animaciones excesivas y estados de formularios. Cada problema se documenta junto con su solución y prueba.

  6. 6 · Integramos y verificamos

    Hicimos: revisamos responsive, teclado, foco, accesibilidad, formularios, multimedia, navegación y documentación. Decidimos: conservar una instantánea de commits para que la bitácora siga siendo legible aunque GitHub no responda.

  7. 7 · Documentamos la trazabilidad

    Hicimos: vinculamos etapas, responsables, commits y Pull Requests. Resultado: GitHub aporta la evidencia del cambio y esta página explica por qué se hizo y qué se aprendió.

  8. 8 · Cerramos con aprendizajes y continuidad

    Aprendimos: que modularidad, accesibilidad, rendimiento y control de versiones deben considerarse durante el desarrollo. Próximo paso: trasladar estos criterios al TP2.

02

22–24/09

Identidad visual y Paleta Accesible (WCAG)

Responsable: Equipo Eximia Code

Problema / necesidad

Los cinco perfiles y los recursos visuales podían parecer sitios independientes, y la elección cromática debía garantizar contraste suficiente para todos los usuarios.

Análisis

Se buscaron criterios asociados a software B2B (logística y trazabilidad). Se evaluó el contraste bajo WCAG 2.1 AA y se adoptó la regla 60-30-10 para equilibrar fondos, componentes y focos de interacción.

Decisión + justificación

Se definió un orden de producción (logo → panel → avatares) y se centralizó la paleta en tokens CSS. En modo claro destaca #070D1F sobre #FFFFFF y en modo oscuro #FFFFFF sobre #0B132B (superando la relación 4.5:1). Para acciones y focos visibles de teclado se fijaron acentos de alto contraste (#D9381E / #FFB703) sin basar la información únicamente en el color.

Dificultad → solución → resultado

La dificultad fue mantener la coherencia visual entre recursos heterogéneos sin perder legibilidad en modo oscuro. Se ajustaron los bordes a #6B829B y se validó la composición y contraste de cada avatar antes de su integración. Resultado: un lenguaje visual común, unificado y totalmente accesible.

Arquitectura de archivos y CSS

Responsable: Equipo Eximia Code

Problema / necesidad

El proyecto tendría portada, cinco perfiles, formularios, Bitácora, responsive, accesibilidad y múltiples interacciones.

Análisis

Decisión + justificación

Se eligió una arquitectura modular: 01-variables.css, 02-base.css, 03-layout.css, 04-portada.css, 05-perfil.css, 06-formularios.css, 07-bitacora.css, 08-responsive.css y 09-accesibilidad.css.

Separar demasiado también podía complicar el mantenimiento. Se asignó una responsabilidad clara a cada archivo. La arquitectura se convirtió en una herramienta de colaboración.

25–27/09

Responsive y accesibilidad

Responsable: Equipo Eximia Code

Problema / necesidad

El sitio debía adaptarse a 400, 900 y 1200 px sin perder jerarquía ni generar desplazamiento horizontal.

Análisis

Se identificaron como componentes sensibles el menú, grillas, tarjetas, formularios, imágenes y navegación de perfiles.

Decisión + justificación

Se utilizarían Grid, Flexbox, media queries, unidades relativas, max-width y reorganización de columnas. Se incorporaron foco visible, skip-link, ALT, labels, ARIA, prefers-reduced-motion, prefers-contrast y forced-colors.

Dificultad → solución → prueba

El riesgo principal era el overflow. Se planificó revisar cada breakpoint y el recorrido con Tab. El criterio de accesibilidad quedó incorporado desde el diseño, no como parche final.

26–28/09

Optimización de imágenes y multimedia

Responsable: Equipo Eximia Code

Problema / necesidad

Los avatares, posters, álbumes y recursos de portada podían aumentar innecesariamente el peso del sitio.

Análisis

Se evaluó el tamaño necesario según el contexto de uso y la densidad visual.

Decisión + justificación

WebP, versiones de 400 px, srcset, sizes, loading="lazy", dimensiones explícitas y precarga cuando correspondiera.

Dificultad → solución → aprendizaje

Reducir demasiado la resolución afectaba calidad. Se mantuvieron fuentes de mayor resolución para contextos principales y versiones más pequeñas para tarjetas. Optimizar significó equilibrar peso y calidad.

Dificultades transversales

Problema → análisis → solución → prueba

Overflow horizontal

Problema: grillas, tablas o textos largos podían generar desplazamiento lateral. Solución: componentes con min-width:0, grids fluidas, overflow-wrap:anywhere, límites de ancho y, en el historial, tarjetas apilables en lugar de tablas anchas. Prueba: revisión a 400, 900 y 1200 px.

Historial de Git demasiado ancho

Problema: una tabla con muchas columnas podía convertirse en un cuadro con scroll horizontal. Solución: el historial se representa como tarjetas de commits, donde cada registro muestra fecha, responsable, tipo, título/descripción y enlace. Resultado: el historial puede leerse en móvil sin desplazamiento horizontal.

Imágenes sobredimensionadas

Problema: descargar siempre los originales aumentaba el peso. Solución: WebP, 400 px, srcset y sizes. Prueba: revisión visual y de dimensiones según contexto.

Animación excesiva

Problema: demasiada transición podía generar ruido o incomodidad. Solución: microinteracciones puntuales y prefers-reduced-motion. Prueba: desactivación de movimiento cuando el sistema lo solicita.

Multimedia pesada

Problema: iframes cargados desde el inicio. Solución: Spotify bajo demanda. Prueba: el reproductor se crea únicamente al solicitarlo.

Formulario sin recarga

Problema: se necesitaba comunicar estados sin abandonar la página. Solución: validación + fetch AJAX + ARIA + foco. Prueba: campos obligatorios, formato de email, longitud y mensajes.

Cierre del TP1

Qué aprendimos

Eximia Code permitió transformar una problemática previamente analizada en una experiencia frontend completa. El trabajo mostró que desarrollar una interfaz implica investigar, tomar decisiones, implementar, encontrar dificultades, resolverlas, probarlas e integrarlas.

La organización por ramas, commits y Pull Requests permitió distribuir responsabilidades y conservar trazabilidad. La Bitácora complementa ese historial explicando el motivo de las decisiones y el aprendizaje obtenido.

La Bitácora registra el camino además del resultado.Investigación → decisión → implementación → dificultad → solución → prueba → integración → aprendizaje.
